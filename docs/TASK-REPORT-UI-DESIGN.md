# Better Email 界面设计任务报告

> 状态：待产品审计
>
> 版本：2026-08-07
>
> 范围：桌面端邮箱主工作台、阅读、写信、设置中心及其共享组件

## 0. 报告目的

这份报告用于建立下一轮界面设计和实现的共同基线。它不直接修改界面代码，也不把现有入口描述成需要重做的功能。

报告的审计对象有三类：

1. 现有产品是否已经具备清楚且可持续的界面信息架构。
2. 视觉系统是否有唯一来源，能否支持长期迭代而不继续叠加覆盖层。
3. 下一轮改造是否能在不破坏邮件数据边界、撤销、同步和安全状态的前提下逐步交付。

## 1. 结论摘要

Better Email 已经不是概念稿，而是一个功能边界较深的本地优先桌面邮箱。主界面的三栏工作区、邮件列表、阅读面板、写信窗口和设置中心都已经拆出相对明确的 React 组件，邮箱整理、搜索、会话、附件、账号连接、同步诊断和安全预览均有实现入口。

当前最重要的问题不是“增加更多功能”，而是降低长期使用时的认知噪音，并让视觉规则有单一、可追踪的来源。当前 CSS 由旧版样式、`2026` 目录样式、多个 `pass-*` 修正文件和设置专用 token 并行组成，累计样式文件接近 12,500 行。它们可以快速修正单个回归，但会增加覆盖顺序、状态一致性和后续审计成本。

建议的方向是：

- 保留现有三栏和渐进披露的信息架构。
- 以“本地工作台”而不是“营销型 SaaS”作为视觉注册。
- 把设计 token、状态语义和共享组件契约统一起来。
- 先稳定主工作台的高频路径，再处理设置中心的长尾页面。
- 每一轮只改变一个用户能感知的层级问题，并用截图、交互回归和键盘回归验收。

## 3. 当前产品与界面资产盘点

### 3.1 产品定位

产品定位已经在 [`docs/DESIGN.md`](/Users/pyu/code/better-email/docs/DESIGN.md:1) 中明确：

- Tauri + Rust + React + SQLite 的本地优先桌面邮箱。
- 传统三栏工作方式，优先保证本地工作台清楚、可恢复、可诊断。
- 邮件头先同步，正文和附件按需获取。
- HTML 邮件清洗，远程图片默认阻止。
- 低频设置渐进披露，高频邮件动作直接可见。

这些边界应继续保留，设计改造不应把产品变成聊天应用、信息流或营销首页。

### 3.2 现有高频能力

- 统一邮箱和单账号范围切换。
- 收件箱、已发送、草稿箱、归档、废纸篓、垃圾邮件和稍后处理。
- 邮件模式与会话模式切换。
- 搜索范围、筛选、排序、保存搜索和加载更多。
- 标星、已读、归档、删除、移动、标签、垃圾邮件和稍后处理。
- 右键菜单、拖拽到文件夹、批量选择和七秒撤销。
- 阅读正文安全提示、远程图片信任、附件按需下载和快速回复。
- 写信、回复、回复全部、转发、草稿自动保存、模板、身份、附件和撤回发送。
- 账号、服务商、认证、发送、通知、隐私、身份、同步、联系人、规则和安全预览设置。

### 3.3 当前组件边界

React 组件边界总体方向正确。`App` 负责应用状态和跨领域编排，`MessageListPane`、`ReaderPane`、`Sidebar`、写信和设置分别承载界面区域，领域 Hook 负责数据、撤销、同步、联系人和账号连接。

需要注意的是，组件边界清楚不等于视觉契约清楚。下一轮应为共享组件补充统一的状态、尺寸、键盘和文案契约，避免每个领域继续自行定义按钮、面板和状态颜色。

## 4. 设计问题诊断

优先级定义：

- P0：会影响整体设计系统稳定性或审计可信度的问题。
- P1：会明显影响高频工作流和长期扫描效率的问题。
- P2：局部体验、视觉精度或后续维护成本问题。

### P0. 样式来源不唯一

`src/App.tsx` 同时引入 [`src/styles.css`](/Users/pyu/code/better-email/src/styles.css:1) 和 [`src/ui-2026.css`](/Users/pyu/code/better-email/src/App.tsx:107)。两套入口各自再引入布局、侧栏、列表、阅读、弹层和响应式样式。`ui-2026.css` 另外叠加多个 `pass-*` 文件，导致最终规则依赖 import 顺序和局部选择器权重。

**影响**：无法快速回答“一个状态颜色或间距应该改在哪里”，也无法保证写信、阅读和设置的同类控件同步变化。

**建议**：建立单一 canonical CSS 入口，保留迁移兼容层但停止新增 `pass-*` 文件。新 token 和共享组件只能从 canonical 层消费。

### P1. 视觉层级已经清楚，但状态表达略重

当前选中态使用浅蓝背景和内嵌蓝色侧边标识，主要按钮使用高饱和蓝色，搜索区、工具栏、标签和安全提示也反复使用蓝色。单个状态并不错误，但叠加后会让蓝色从“状态”变成“装饰”。

**建议**：

- 选中态优先使用明度差和文字权重，不再依赖明显的侧边条。
- 蓝色只承担主要操作、焦点、链接和同步进行中状态。
- 未读使用字重和小圆点，重要使用独立的暖色语义，危险使用红色，成功使用绿色。
- 警告面板保持背景色提示，但动作按钮不要全部使用同一高亮色。

### P1. 邮件列表的信息密度高，但缺少“主扫描线”

邮件行同时呈现头像、发件人、时间、主题、摘要、星标、重要、附件和未读状态。信息完整，但视觉重量相近，用户需要反复在多个小元素之间跳转。

**建议**：

- 每行固定为三条扫描线：发件人与时间、主题与状态、摘要与辅助元数据。
- 只有未读邮件使用更强字重；已读邮件降低摘要对比度。
- 附件和标签作为行尾的辅助元数据，不与主题争夺第一视觉层级。
- 日期分组成为真正的节奏节点，而不是另一条细边界。

### P1. 设置中心功能拆分合理，但仍然有页面级“表单堆叠”风险

设置已经拆分为独立页面，且支持桌面侧栏、窄屏选择器和底部分页。但账号、服务商、认证和同步页面包含大量技术说明、诊断、验证和高级选项。

**建议**：

- 每个页面首屏只回答“当前状态是什么”和“下一步是什么”。
- 低频技术详情保持折叠，失败状态直接提供修复动作。
- 账号首页显示账号健康、默认发件身份、最近同步和需要处理的异常，不把完整配置表单放在首屏。
- 连接相关页面共享同一条四阶段诊断组件，不再各自设计状态卡片。

### P2. 旧 token、2026 token 和设置 token 仍存在语义重复

全局 token 中同时存在 `--ui-*`、旧的 `--surface-*`、`--text-*`、`--line-*` 和 `--shadow-*` 映射；设置中心又有 `--st-*` 体系。

**建议**：保留领域前缀，但将它们映射到同一套语义 token，例如 `--color-surface-canvas`、`--color-text-primary`、`--color-state-warning`。组件不应直接引用页面专用 hex 值。

### P2. 测试断言与安全文案存在契约漂移

当前 UI smoke 在安全提示处等待的文本与实际页面文本不一致。安全流程本身已经渲染，但测试失败意味着文案、组件和验收标准没有共享一份稳定契约。

**建议**：将安全状态文案抽成纯配置或纯函数，并让组件测试和 UI smoke 共用状态 ID，而不是只匹配自由文本。

## 5. 目标设计方向

### 5.1 设计注册

**产品注册**：成熟桌面工具。

**物理场景**：用户在白天或夜间的桌面显示器前，连续处理几十到几百封邮件，窗口长期打开，注意力集中在内容和下一步动作上，而不是界面装饰上。

**目标感受**：昂贵、安静、可靠、熟悉，但不是冷漠或空洞。

### 5.2 设计原则

1. **内容先于容器**：邮件内容、发件人、时间和状态优先，卡片和边框只在真正需要分组时出现。
2. **状态必须可解释**：颜色、字重、图标和文案共同说明“发生了什么”和“下一步能做什么”。
3. **高频动作不隐藏**：回复、归档、已读、删除、标星等保持直接可见；移动、标签、稍后处理和导出按组进入更多菜单。
4. **渐进披露技术复杂度**：服务商、认证、诊断和协议详情先展示结果，再展示解释，最后才展示原始技术信息。
5. **桌面密度来自节奏**：用固定行高、明确扫描线和稳定对齐提升密度，不靠缩小文字或堆叠边框。
6. **动作必须可恢复**：邮件移动、归档、删除、标签、稍后处理和发送都保留明确撤销或恢复路径。

### 5.3 明确避免

- 大面积玻璃、背景模糊和装饰性渐变。
- 统一大小的营销卡片网格。
- 聊天气泡、社交信息流和过度头像化的消息语义。
- 用彩色侧边条标记每一种状态。
- 用多个蓝色浅底同时表达选中、提示、链接和成功。
- 用大标题、巨大数字或 Hero 页面占用工作区首屏。

## 6. 统一设计系统方案

### 6.1 Token 层级

建议分三层，禁止组件直接写页面级颜色：

```text
Primitive
  灰阶、蓝阶、暖色、红色、绿色、尺寸单位

Semantic
  canvas、surface、text、border、focus、selected、unread、warning、danger、success、sync

Component
  message-row、toolbar、dialog、settings-page、toast、attachment-row
```

推荐的基础节奏：4、8、12、16、20、24、32、40。邮件行、按钮、输入框和工具栏必须使用固定的尺寸 token，避免动态内容改变布局。

### 6.2 颜色语义

采用低彩度中性表面，保留一个受控蓝色作为主交互色。建议至少定义：

| 语义 | 用途 | 视觉要求 |
| --- | --- | --- |
| `text-primary` | 发件人、主题、页面标题 | 最高正文对比度 |
| `text-secondary` | 摘要、辅助说明 | 清晰但不抢主层级 |
| `text-tertiary` | 时间、数量、技术细节 | 只承担辅助信息 |
| `state-accent` | 主要操作、焦点、链接 | 限制使用范围 |
| `state-selected` | 当前文件夹、当前邮件 | 依赖明度和字重，避免重边框 |
| `state-unread` | 未读邮件 | 字重和未读点优先 |
| `state-warning` | 远程图片、风险、部分成功 | 暖色背景，动作保持克制 |
| `state-danger` | 永久删除、移除账号 | 只用于危险动作和错误 |
| `state-success` | 保存、同步、验证成功 | 只在结果确认时出现 |

### 6.3 共享组件清单

| 组件 | 统一职责 | 必须覆盖的状态 |
| --- | --- | --- |
| `AppShell` | 三栏布局、宽度持久化、窗口级层级 | 默认、调整中、窄窗口 |
| `PaneResizer` | 侧栏和列表宽度拖拽 | 默认、悬停、拖拽、键盘不可用提示 |
| `AccountSwitcher` | 统一邮箱、单账号和服务商摘要 | 当前账号、统一邮箱、账号异常、无账号 |
| `SidebarNavItem` | 文件夹、数量、收藏和右键入口 | 默认、悬停、选中、未读、拖拽目标、禁用 |
| `MessageRow` | 发件人、主题、摘要、时间和辅助状态 | 已读、未读、选中、重要、附件、会话 |
| `MessageToolbar` | 搜索、筛选、排序、批量操作 | 默认、批量选择、刷新中、无结果 |
| `ReaderHeader` | 主题、发件人、时间和高频动作 | 普通邮件、线程、草稿、已发送、垃圾邮件 |
| `SecurityNotice` | 风险说明和下一步动作 | 阻止、部分允许、已信任、链接风险 |
| `AttachmentRow` | 附件元数据、下载、打开和失败恢复 | 未下载、下载中、已下载、失败、受限 |
| `Composer` | 收件人、主题、正文和工具区 | 新建、回复、草稿恢复、自动保存、发送撤销 |
| `SettingsFrame` | 设置导航、页头、保存和连接测试 | 未保存、保存中、验证中、失败、成功 |
| `ToastStack` | 结果反馈和撤销 | 成功、警告、错误、普通撤销、撤销发送 |
| `ContextMenu` | 低频动作和危险动作分组 | 普通、子菜单、键盘导航、边界修正 |

每个共享组件都应有：尺寸约束、ARIA 名称、键盘行为、禁用条件、错误文案和截图样本。组件测试不只检查是否渲染，还要检查状态之间的视觉和交互差异。

## 7. 页面与工作流拆分

### 7.1 主工作台

```text
AppShell
  Sidebar
    Brand / AccountSwitcher
    Compose
    PrimaryFolders
    SecondaryTools
    SyncStatus
    Settings / Shortcuts

  MessageListPane
    SearchToolbar
    ViewMode / Filter / Sort
    BulkToolbar
    DateGroups
    MessageRow or ThreadRow

  ReaderPane
    ReaderToolbar
    SenderIdentity
    SecurityNotice
    BodyContent
    Attachments
    QuickReply
```

主工作台不新增独立首页，不加入欢迎 Hero，不把邮件内容包在多层卡片内。

### 7.2 阅读工作流

- 普通邮件：主题和发件人优先，回复、回复全部、转发、归档、已读、删除和标星直接可见。
- 线程：默认选择最新邮件，线程内部保持同一套高频操作，静音、移动和标签进入更多菜单。
- 安全邮件：先显示阻止原因，再显示安全动作，技术详情和原始链接渐进展开。
- 附件：先显示数量、类型和大小，下载后才显示打开或另存为。
- 空状态：明确当前范围、搜索条件或同步状态，并提供一个直接动作。

### 7.3 写信工作流

- 默认只显示收件人、主题和正文。
- 抄送、密送、发件身份、模板、签名、富文本、附件和稍后发送进入工具区。
- 自动保存状态紧贴标题或底部状态栏，不使用大提示卡。
- 发送后撤销作为独立计时提示，不与普通邮件撤销混淆。
- 关闭有未保存内容时优先内联说明或紧凑确认，不把确认弹窗作为默认交互。

### 7.4 设置中心

设置继续保持左侧分类和单一内容滚动区，但统一页面结构：

```text
SettingsFrame
  Header: 当前页、保存、测试连接、关闭
  Navigation: 分组、搜索、当前页
  PageHeader: 分组名、页面名、状态摘要
  PrimaryContent: 常用设置和当前状态
  AdvancedDisclosure: 技术详情、协议参数、原始响应
  PageFooter: 上一页、下一页、保存结果
```

页面分组建议：

- 账号：账号列表、服务商、认证、身份。
- 工作流：发送、通知、同步、规则。
- 数据与隐私：本地存储、联系人、隐私、安全预览、模板。

这不是减少页面功能，而是让用户更容易理解页面之间的关系。当前已有的 12 个页面仍可独立渲染。

## 8. 工程落地方案

### 8.1 样式整理

1. 选定 `src/ui-2026.css` 为唯一 canonical 入口。
2. 将旧版 `src/styles.css` 标记为兼容迁移层，停止新增规则。
3. 合并重复的布局、侧栏、列表、阅读和弹层规则。
4. 将 `pass-*` 文件按职责合并为少量领域文件，例如 `message-list.css`、`reader.css`、`settings.css`、`overlays.css`。
5. 将 `--ui-*`、旧兼容 token 和 `--st-*` 映射到同一套语义 token。
6. 新增 lint 或脚本，阻止组件样式直接写页面级 hex 颜色。

### 8.2 React 边界

现有组件拆分不需要大规模重写。优先补充共享组件契约和状态配置，减少 `App.tsx` 中直接传入的视觉分支。业务 Hook 和 Tauri 调用边界保持不变。

建议新增或明确的纯配置：

- `src/app/uiTokens.ts`：状态和尺寸语义。
- `src/app/uiCopy.ts`：安全、同步、撤销和诊断文案。
- `src/components/shared/StatusPill.tsx`：统一状态显示。

这些组件只在确实减少重复时创建，不建立新的 UI 框架。

### 8.3 数据和状态边界

设计改造不得改变以下行为：

- 账号凭据仍只进入系统 Keychain。
- 邮件正文和附件仍按需加载。

- 统一邮箱和单账号范围不可混淆。
- 连接测试、只读验收和写入验收保持不同权限和结果状态。

## 10. 验收标准

### 10.1 视觉

- 同类控件在主工作台、写信和设置中心使用同一组尺寸、圆角和状态颜色。
- 页面不依赖明显的彩色侧边条来表达选中或告警。
- 主要操作最多使用一个高强调色，警告和危险状态不会被蓝色淹没。
- 邮件主题和发件人始终高于摘要、时间和附件元数据。
- 文字、图标、徽标、按钮和弹层在 430px 宽度内不发生横向溢出或重叠。

### 10.2 交互

- `Cmd/Ctrl + A`、`S`、`M`、`E`、删除和 `Esc` 行为保持现有约定。
- 鼠标、键盘和右键菜单能完成同一组核心邮件操作。
- 所有破坏性操作都有明确范围、确认条件和可恢复路径。
- 连接测试和保存并验证不会误用其他账号凭据。
- 低频操作的折叠状态不会隐藏当前错误或阻塞下一步动作。

### 10.3 无障碍

- 所有纯图标按钮有 `aria-label` 和 tooltip。
- 焦点环可见，且不依赖颜色作为唯一状态信息。
- 文字和控件达到 WCAG AA 对比度目标。
- 支持 `prefers-reduced-motion`，关闭非必要位移动画。
- 设置、菜单、弹窗和写信窗口有稳定的焦点进入、循环和恢复路径。

### 10.4 工程与性能

- 首屏仍只加载三栏工作区、列表和阅读面板，写信和设置保持延迟加载。
- 样式新增不再增加 `pass-*` 覆盖文件。
- 业务 Hook、Tauri 命令、凭据边界和 SQLite 数据模型不因视觉重构改变。
- 视觉回归失败可以定位到 token、组件或页面，而不是只能通过选择器权重猜测。
