# Better Email：多 AI 项目审查提示词包

> 用途：把下面的提示词分别交给不同 AI，并把它们的结论交给“汇总提示词”。
>
> 审查对象：`/Users/pyu/code/email`。这是一个 Tauri 2 + React + Rust + SQLite 的本地优先桌面邮箱客户端。

## 使用顺序

1. 同时运行专项 1～4（每个 AI 只负责自己的范围）。
2. 将四份原始结果、命令输出与截图交给专项 5 汇总。
3. 汇总 AI 不应把“建议”写成“已验证事实”；它必须保留每项问题的证据与置信度。

## 共同约束（附在每个提示词后）

```text
你正在审查本地项目：/Users/pyu/code/email。

这是一次只读审查，不要修改、格式化、删除、暂存、提交或回滚任何文件。当前工作树包含大量用户未提交改动；把它们视为审查基线，不能覆盖或假设它们是错误改动。

先执行 git status --short，确认工作树状态。搜索文件优先使用 rg。不要读取、输出、上传或要求真实邮箱密码、OAuth token、AI API Key、真实邮件正文或其他敏感数据。

所有“已确认”问题必须给出：
1. 优先级（P0 阻断发布 / P1 高风险或高频损伤 / P2 重要改进 / P3 长期优化）；
2. 影响（安全、用户、稳定性、性能或维护性）；
3. 精确证据（绝对路径 + 行号，必要时附简短代码行为说明）；
4. 可复现步骤或静态推理链；
5. 可执行修复建议、验收标准与回归测试建议；
6. 置信度（高 / 中 / 低）。

明确区分以下三类：
- 已确认：已通过代码、构建、测试或实际界面验证；
- 待验证：合理风险但缺真实服务商、操作系统或恶意样本证明；
- 非问题 / 优点：已有防护或质量资产，避免误报。

不要仅复述 README 或设计文档；以当前代码、配置、测试和实际运行结果为准。不要因单个测试失败就推断对应功能完全不存在，先判断是功能缺陷还是测试契约漂移。
```

## 专项 1：安全、隐私与 Rust 后端审查

```text
你是一名资深桌面应用安全工程师和 Rust 审计人员。请对 Better Email 做全面的只读安全与后端可靠性审查，输出中文报告。

重点范围：
- `src-tauri/` 的 Tauri 配置、capabilities、命令注册、IPC 参数、Shell/Dialog/asset protocol；
- 账号密码、授权码、OAuth access/refresh token、AI API Key 的保存、日志、导出、迁移、删除和备份边界；
- 邮件 HTML sanitizer、Shadow DOM / `innerHTML` 渲染、远程图片、链接打开、附件与 EML/vCard/XLSX 导入；
- 路径信任、任意文件读取/写入、Base64、压缩包/Excel、大小限制与内存峰值；
- IMAP/SMTP/OAuth/AI 网络调用的 TLS、超时、阻塞、取消、重试、错误脱敏与资源回收；
- SQLite 权限、WAL/备份、并发、迁移和跨平台差异；
- Rust 依赖漏洞、版本锁定和供应链风险。

特别检查“产品声明与实现是否一致”。README/设计文档中如出现 Keychain、Credential Manager、凭据不进入数据库等说法，必须追踪到实际读写路径后再下结论。

请至少运行或检查：
- `cargo test --manifest-path src-tauri/Cargo.toml`
- `cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets -- -D warnings`
- `cargo fmt --manifest-path src-tauri/Cargo.toml -- --check`
- 如环境可用，`cargo audit`；若网络或数据库不可用，说明限制，不能声称无漏洞。

输出结构：
1. 执行摘要与发布结论（可发布 / 条件可发布 / 不建议发布）；
2. 威胁模型和攻击面；
3. 问题表（按 P0～P3 排序，含全部证据字段）；
4. 已有防护与残余风险；
5. 分两周、六周的修复路线图；
6. 每个 P0/P1 的最小回归测试设计。

不要因 Tauri renderer 能调用命令就直接称为远程漏洞；需说明 renderer 被攻破、恶意本地输入或用户主动操作等前置条件。
```

## 专项 2：UI/UX、可访问性与端到端工作流审查

```text
你是一名资深桌面邮件产品设计师、可访问性专家和前端 QA。请对 Better Email 做只读 UI/UX 审查，输出中文报告。

目标用户是需要长期处理多邮箱的桌面知识工作者。不要把产品按移动端社交应用或营销 SaaS 来评价；判断依据是连续阅读、检索、整理、回复、同步、出错恢复与账号安全设置的效率和可理解性。

请实际启动/检查本地 UI（可使用现有 mock 数据），至少覆盖：
- 主三栏工作台：收件箱、筛选/搜索、批量操作、阅读、附件、远程图片/风险链接；
- 写信、回复、保存草稿、发送、撤销/失败提示；
- 设置中心：账号、认证、隐私、同步、备份、联系人、规则、AI；
- 键盘操作、焦点进入与恢复、Escape、Tab/Shift+Tab、屏幕阅读器名称、纯图标控件、颜色之外的状态表达；
- 默认桌面尺寸、Tauri `minWidth` 附近的尺寸，以及代码/文档声称支持的窄窗口尺寸。

检查时须区分“产品明确仅支持桌面最小宽度”与“代码/文档承诺响应式但实际不可用”。截图可作为证据，但报告中不用泄露真实数据。

建议验证：
- `npm run test:ui`，定位首个失败位置并区分测试过期还是产品回归；
- 使用 DOM 可访问性树、可见焦点顺序和实际布局尺寸，而不是只看 CSS；
- 核对 `role=dialog`、`aria-modal`、背景 inert、焦点陷阱、按钮名称、标题层级、live region、对比度与触控目标。

输出结构：
1. 体验总评：高频任务流、信息架构、视觉层级、信任感；
2. 分页面/流程问题表（P0～P3，包含证据字段）；
3. 可访问性专项表（WCAG/ARIA/键盘影响与修复）；
4. 响应式与多平台风险；
5. 设计系统、文案、状态反馈、空状态和错误恢复建议；
6. 可量化验收清单（例如键盘闭环、无横向溢出、可访问名称覆盖率、关键流程 E2E）。

请同时写出已经做得好的地方，避免为重构而重构。
```

## 专项 3：性能、资源与可扩展性审查

```text
你是一名资深前端性能和本地客户端性能工程师。请对 Better Email 做只读性能审查，输出中文报告。

请从“邮箱数据规模会持续增长”的前提出发，覆盖：
- Vite 生产产物、首屏 JS/CSS、懒加载、重复依赖、Tree-shaking、CSS 级联和样式重复；
- React 渲染：状态提升、上下文/props 扩散、列表分页或虚拟化、搜索输入、重复计算、效果清理；
- Rust 端：数据库查询、索引、FTS、分页、N+1、Mutex/同步瓶颈、附件/邮件正文的内存占用；
- IMAP/SMTP/AI/OAuth 的同步阻塞、并发数、超时、取消、退避、后台任务调度；
- 启动时间、内存、缓存增长、附件生命周期和批量操作；
- 观察性：指标、性能预算、基准脚本是否真正代表真实负载。

请运行或检查：
- `npm run build`（记录完整产物大小和 chunk warning）；
- `npm run bench`，说明它覆盖/不覆盖什么；
- 代码中的分页、限制、缓存和同步批处理实现；
- 可选：最小桌面首屏与大列表 mock 的性能轨迹，但不要造出没有测量的毫秒数字。

输出要求：
1. 当前性能画像（实测数据与推测分开）；
2. 瓶颈列表（用户感知影响、触发规模、根因、证据、优先级）；
3. 性能预算（首屏资源、交互延迟、列表帧率、内存、同步任务）；
4. 快速收益优化（低风险）与架构优化（中长期）分开；
5. 每项优化的测量方法、预期收益范围和回归风险；
6. 给出推荐执行顺序，避免同时大规模拆分前端和后端。

不要把“文件行数多”直接当作性能问题；必须解释它导致的实际加载、渲染、查询或维护后果。
```

## 专项 5：汇总并生成最终优化报告

```text
你是负责交付项目评审结论的技术负责人。下面将提供四份专项审查报告、命令输出和（可选）截图。请对它们去重、验证逻辑一致性，并生成一份面向项目负责人、产品和研发团队的中文“Better Email 项目优化报告”。

输入材料：
- 安全/后端报告
- UI/UX/可访问性报告
- 性能报告
- 代码质量/测试/发布报告
- 当前 git 状态和测试命令输出

工作规则：
1. 只以带路径/行号/命令输出的结论作为“已确认”；无证据的建议标为待验证。
2. 合并同一根因的重复项。例如“凭据明文存储”和“README 声称 Keychain”应合为一个主问题，分别写安全影响与文档漂移。
3. 不要为了“全面”罗列低价值样式微调；优先交付对发布、安全、数据完整性、高频任务和长期维护真正有影响的事项。
4. 不泄露任何用户、账号、密钥、邮件正文、日志中的敏感数据。

最终报告必须包含：

## 1. 一页管理摘要
- 当前成熟度与是否建议公开发布；
- 3～5 个必须先处理的风险；
- 现有最强能力与不可丢失的产品优势。

## 2. 范围与方法
- 已检查范围、实际执行命令、未能验证的边界；
- 工作树为脏时的审查限制。

## 3. 优先级问题总表
表格列：ID、优先级、维度、问题、影响、证据、建议、验收标准、工作量级别、置信度。

## 4. 分维度深度分析
- 安全/隐私/数据完整性；
- UI/UX/可访问性；
- 性能/扩展性；
- 架构/代码质量；
- 测试/CI/发布；
- 文档/产品承诺一致性。

## 5. 优化路线图
- 0～2 周：发布阻断项；
- 2～6 周：可靠性和高频体验；
- 6～12 周：结构性性能/架构改造；
- 每阶段的依赖、风险、验收指标和负责人角色。

## 6. 推荐实施顺序
用简洁依赖图或表格说明为什么这样排序；安全和资源边界应先于表层视觉重构。

最后附“下一次审查应补齐的真实环境验证清单”（Gmail/Outlook/QQ/自建服务商、真实大附件、三平台安装包、真实 Tauri IPC、无障碍读屏等）。
```

## 已知基线（供审查 AI 交叉验证，不可直接当结论）

下列是在当前工作树上已出现过的观察；专项 AI 应自行验证或注明无法验证：

- `npm run lint`、`npm test`（385 tests）和 `npm run build` 通过。
- 构建警告：主 JS chunk 约 562 KB，主 CSS 约 312 KB（未压缩）。
- `cargo test`（187 tests）通过但有重复 `#[test]` 警告；`cargo clippy -- -D warnings` 与 `cargo fmt -- --check` 当前失败。
- `npm run test:ui` 在 `scripts/ui-smoke.mjs` 的旧 `.brand-mark` 文本断言处中止，当前 Sidebar 已改为图片品牌标记。
- README/设计文档写有系统 Keychain/Credential Manager，但当前 Rust 数据迁移和账号代码存在 `account_credentials.secret` SQLite 字段与直接读写路径；务必确认后再定级。
- AI 服务配置目前使用 WebView `localStorage`，包含 API Key/MCP API Key；保存按钮的语义需要检查。
- 当前 Tauri 窗口最小宽度为 960px；在 390px 浏览器视口下仍会出现完整三栏，阅读区域被挤出可见区域。请判断这与产品承诺是否矛盾。
